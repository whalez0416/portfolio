Concept

다 같은 길을 가고 있었고,
나는 내려섰다.

포트폴리오를 읽게 하는 대신 조작하게 합니다. 도구를 하나 주울 때마다 할 수 있는 일이 하나씩 늘어나고, 그 동사가 곧 그 도구의 주장입니다.

00thesis

한 줄 정의

검색 순위를 팔던 무리와 같은 포장도로에서 출발해, 갈림길에서 혼자 내려선 뒤, 길에서 도구 8개를 주우며 측정 → 생산 → 감시 → 확장을 차례로 할 수 있게 되는 약 4분짜리 게임. 각 도구는 설명되지 않고 능력으로 주어집니다.

전제는 하나입니다 — 메커니즘이 곧 논증이다. "측정되지 않던 것을 계측한다"는 문장을 읽히는 대신, 랜턴을 줍기 전까지 크롤러를 아예 보이지 않게 만들어 못 보는 상태를 겪게 합니다. 플레이어가 "안 보이네"라고 느낀 뒤에 도구를 주우면, 그 도구가 무엇인지 설명할 필요가 없습니다.

01why재설계 사유

이전 버전은 왜 실패했나

직전 버전에도 횡스크롤 "여정"이 있었지만, 실제로는 가로 스크롤바에 기둥 8개를 꽂아둔 목차였습니다. 기둥에 닿으면 게임이 멈추고 텍스트 모달이 떴습니다. 게임으로 보는 게 아니라 게임으로 메뉴를 여는 구조였습니다.

이전
흰 막대기 캐릭터 · 걷기만 가능 · 정거장에 닿으면 정지 후 모달 · 8개 기둥이 전부 동일 · 서사 없음 · 실패도 위험도 없음
현재

02structure프롤로그 + 5막

구조 — 도구 = 동사

도구는 8개, 전부 실제 저장소가 있는 프로젝트입니다. 게임은 이 8개를 능력 해금 순서로 재배열했을 뿐, 없는 것을 만들지 않았습니다.

막도구열리는 동사서사

1 · 위협 — 없음. 점프해도 아무 일도 안 일어남 혼자가 됐고, 방문자가 떠나는 걸 보기만 한다

닫히는 구조

1막에서 회색 방문자들이 하나씩 위로 빨려 사라지고, 화면이 어두워지고, 플레이어는 아무것도 못 합니다. 5막 끝에서 파란 방문자들이 병원으로 걸어 들어옵니다. 같은 그림의 방향만 뒤집은 것이고, 그 사이를 채운 것이 도구 8개입니다.

03camera시점 전환

왜 위에서 내려다보다가 옆으로 눕나

연출이 아니라 필요입니다. 횡스크롤은 길이 한 줄이라 "다른 길로 갔다"를 그릴 방법이 없습니다. 갈림길을 보여주려면 위에서 봐야 합니다.

그리고 위에서 내려다보면 정수리만 보입니다. 무리 속에서 정수리는 다 똑같이 생겼고, 그중 하나만 흰색에 앰버 점이 찍혀 있습니다. "여럿이 같이 출발했다"를 한 프레임으로 말하는 각도입니다.

갈림길에서 포장도로 아래로 내려서면 정수리 화면이 수평선 쪽으로 눌리면서 그 아래에서 횡스크롤 세계가 올라옵니다. 카메라가 눕는 1.15초가 그대로 전환 연출입니다. 무리는 계속 직진해서 길 끝에서 사라집니다.

이탈 판정

흙길은 시선을 끄는 장치일 뿐 판정 영역이 아닙니다. 처음엔 28px 밴드 위를 정확히 밟아야 전환되게 만들었는데, 아래로 조금만 더 내려가면 길을 지나쳐 막다른 곳까지 걸어가게 돼서 "갈림길 지나서 포장도로 아래"라는 넓은 영역으로 바꿨습니다. 외줄타기를 시키면 서사가 조작 실수로 무너집니다.

04screens실제 렌더

화면

전부 실제 게임을 헤드리스로 돌려 뽑은 프레임입니다. 목업이 아닙니다. 떠오르는 +1 같은 숫자는 렌더러가 텍스트를 그리지 않아 빠져 있고, 브라우저에서는 표시됩니다.

05rules지켜야 할 것

고쳐도 되는 것과 안 되는 것

고정 1막의 무력함. 아무것도 못 하는 구간을 "지루하다"고 줄이면 전제가 사라집니다.
고정 텍스트 모달로 되돌아가지 않기. 도구를 주우면 판단 한 줄만 배너로 스치고, 전문은 엔딩 링크와 Enter로만 엽니다.
고정 본문은 한 벌. 8개 기록은 페이지 아래 .rec 마크업이 유일한 출처이고, 게임은 그걸 꺼내 씁니다. 게임 안에 설명을 복제하면 두 벌이 어긋납니다.
고정 의존성 0 · 단일 HTML. 빌드도 CI도 패키지도 없습니다. 이 제약 자체가 포트폴리오의 주장 중 하나입니다.
고정 스크롤 우회로. 게임을 안 해도 같은 내용이 아래에 전부 글로 있습니다. 채용담당자가 게임을 강제당하면 안 됩니다.
조정 가능 막의 길이, 도구 배치 간격, 크롤러 밀도, 재크롤 대기(현재 3.5초), 캐릭터 이동 속도
조정 가능 픽셀 아트 전부 — 코드로 그린 ASCII 맵이라 bake() 한 곳만 고치면 CC0 스프라이트시트로 교체 가능
06open논의 필요

결정이 필요한 것들

구현은 끝났지만 아래는 판단이 갈릴 수 있는 지점입니다. 순서는 중요도 순입니다.

Q1 — 가장 중요 게임 안의 숫자가 실적으로 오해될 위험 HUD에 "계측 196 · 발행 37 · 인용 14 · 점유 62%"가 뜹니다. 이건 플레이 점수일 뿐 실제 실적이 아닙니다. 그런데 바로 아래 본문에는 "위키 189페이지", "청구 8.3만 건" 같은 진짜 수치가 있습니다. 채용담당자나 클라이언트가 둘을 섞어 읽으면 신뢰 문제가 됩니다. 게임 숫자에 "이건 플레이 기록입니다" 라벨을 붙일지, 단위를 바꿀지, 아예 뺄지 정해야 합니다.

실물로 확인했습니다. 엔딩의 계측 43과 페이지 상단의 RECORDS 8.3만이 같은 앰버 · 같은 mono · 같은 tabular 숫자 스타일로 렌더됩니다. 구분할 시각적 단서가 하나도 없습니다.
Q2 프롤로그 12.5초 + 본편 3분 — 너무 긴가 30초만 보는 사람에게 프롤로그는 "아직 아무것도 안 나온 구간"입니다. 스크롤 우회로가 있으니 치명적이진 않지만, 프롤로그를 건너뛰는 버튼을 둘지, 무리 구간을 더 짧게 할지 판단이 필요합니다.
Q3 화면의 절반이 빈 하늘 캔버스가 384×216인데 실제 액션은 y 106~178의 얇은 띠에서만 벌어집니다. 캔버스를 384×176 정도로 줄여 화면을 압축할지, 하늘에 요소를 넣을지. 줄이면 페이지에서 차지하는 세로도 590px → 480px로 줄어듭니다.
Q4 캐릭터가 20px — 안경이 안 보임 페이지에서 2.7배로 확대돼 표시되지만 여전히 작습니다. "최희준이라는 사람을 본다"가 목표라면 캐릭터를 키우는 게 맞을 수 있고, 그러면 월드 스케일 전체를 다시 잡아야 합니다.
Q5 모바일 — 조작 불능 버그는 해결, 체감은 미검증 헤드리스 Chrome 430px 뷰포트에서 터치만으로 프롤로그 통과를 확인했고, 진행을 막던 ▼ 버튼 버그도 고쳤습니다. 다만 실제 기기에서의 체감(작은 화면에서 캐릭터가 보이는지, 4버튼이 손에 맞는지)은 아직 모릅니다. 모바일에서는 프롤로그만 보여주고 본편은 스크롤로 유도하는 것도 여전히 선택지입니다.
Q6 게임 이름 현재 가제는 갈림길입니다. 확정 아닙니다. 페이지 안에서는 이름 없이 "읽지 말고, 걸어보세요"로만 안내하고 있어서 이름을 안 붙이고 가는 선택지도 있습니다.
07tech제약 · 검증

기술 현황

구성

  • index.html 한 장이 전부 — 마크업 · CSS · 게임 · 로그 분석기. 외부 에셋 0
  • 캐릭터 · 크롤러 · 페이지 · 정수리 스프라이트는 ASCII 맵을 bake()로 오프스크린 캔버스에 굽는 방식. 프레임당 픽셀 연산 없음
  • 파일은 CRLF · UTF-8. 배포는 main 푸시 → GitHub Pages

검증

  • 인게임 셀프테스트 — 주소에 ?selftest를 붙이면 콘솔에서 검사. 도구↔기록 이름 일치, 세 레인의 난이도 구배(지상 / 점프 / 발판), 발판 착지, 재크롤 대기, 갈림길 이탈 판정
  • 완주 시뮬레이션 — 프롤로그 12.5초 → 시점 전환 → 도구 8/8 → 엔딩까지 헤드리스 자동 플레이
  • 동작 테스트 25종 — 벽 차단 → 되돌아가 습득 → 통과, Enter 일시정지, 재시작 시 프롤로그 복귀 등
  • 렌더 검증 — canvas 2D를 픽셀 버퍼로 직접 구현해 실제 프레임을 PNG로 추출. 위 스크린샷이 그 결과물
  • 실제 Chrome 자동 플레이 — 설치된 Chrome을 헤드리스로 띄워 키 입력을 넣고 끝까지 플레이. 웹폰트 로드 · CSS · DOM HUD 오버레이 · 캔버스 텍스트까지 실물로 검증. 콘솔 오류 0 · 실패 요청 0 · 가로 넘침 없음
  • 터치 전용 플레이 — 430px 뷰포트에서 손가락 터치만으로 프롤로그 통과 확인

저장소 의존성은 여전히 0입니다. 브라우저 구동에 쓴 puppeteer-core는 임시 폴더에만 설치했고, 이미 깔린 Chrome을 재사용해 브라우저를 따로 받지 않았습니다.

렌더링해서 잡은 버그

로직 테스트만으로는 안 잡히던 것들입니다 — KPI 그래프가 지면 한복판에 그려져 건물과 충돌, 심은 페이지가 캐릭터 뒤에 완전히 가려짐, 도로 파손이 세로 창살처럼 보임, 머리카락이 밤하늘과 동색이라 정수리가 사라짐. 화면을 실제로 뽑아보기 전까지 전부 "통과"로 보고되고 있었습니다.

진짜 브라우저를 띄워서 잡은 버그

자체 래스터라이저로도 안 잡히던 것들입니다. 셋 다 사용자가 바로 부딪히는 문제였습니다.

  • 모바일에서 게임 진행 불가 (치명). 터치 패드의 ▼ 버튼이 disabled로 시작해 3막에서야 열리는데, 프롤로그에서 갈림길로 내려가려면 바로 그 버튼이 필요했습니다. 터치 사용자는 길을 벗어날 방법이 없어 막다른 곳에 영원히 갇혔습니다. 이제 프롤로그에서는 이동키, 전환 후에는 발행키로 역할과 라벨이 바뀝니다.
  • 시점 전환 직후 조작 정지. 전환 처리가 눌린 키 상태를 초기화하는데, 물리 키는 계속 눌려 있어 OS 자동반복이 올 때까지(약 0.5초) 캐릭터가 멈췄습니다. 하필 작품의 핵심 순간입니다. 전환 중에는 입력을 읽지 않으므로 초기화 자체가 불필요했습니다.
  • 엔딩 화면 뒤로 HUD가 비침. 스코어보드 위로 "Enter — Hospify 기록 읽기" 큐와 이전 막의 게이지가 그대로 겹쳐 보였습니다.

접근성 감사

Web Interface Guidelines 기준으로 페이지 전체를 감사해 11건을 찾아 전부 고쳤습니다. 수정 후 실제 Chrome에서 20개 항목을 재검증했습니다.

  • 스킵 링크 신설. 페이지가 캔버스 게임으로 시작해 키보드 사용자는 본문까지 게임을 지나야 했습니다. 이제 첫 Tab이 "대표 프로젝트로 건너뛰기"에 닿습니다.
  • 터치 패드 aria-hidden 해제. 포커스 가능한 버튼 4개를 숨긴 컨테이너에 넣는 건 WCAG 4.1.2 위반이고, 터치에서는 이게 유일한 조작 수단입니다. 버튼마다 레이블을 붙였습니다. 타깃 높이 46px로 기준(44px) 충족.
  • 로그 분석기 결과에 role="status". 입력할 때마다 갱신되는데 스크린리더에 통지가 없었습니다.
  • 패드에 touch-action: manipulation. 이동 버튼 연타가 iOS에서 더블탭 확대로 오인되던 문제. 탭 하이라이트 플래시도 제거.
  • 오버레이 스크롤 격리(overscroll-behavior: contain), theme-color 추가, Pretendard CDN preconnect(본문 한글 폰트인데 유일하게 빠져 있었습니다).
  • 막대 그래프를 width → transform: scaleX로 변경 — 입력할 때마다 레이아웃이 발생하고 있었습니다.
  • 텍스트영역 포커스 링 복원(:focus-visible), 곧은 따옴표 → 둥근 따옴표, 도구명에 translate="no".

판단 보류 1건 — 캔버스 게임 루프는 prefers-reduced-motion을 따르지 않습니다. 버튼을 눌러야 시작하는 옵트인이고 시작 전에는 애니메이션 루프가 아예 돌지 않아 의도된 예외로 두었습니다.
